# Changelog

## v0.54.0 — 成绩报告增加「分时期」 (2026-10-24)

### Added: 按题目所属月份拆开，配当期走势

起因是检查「训练有没有进步」。曲线那两张图按**答题顺序**走,而答题是洗牌的
—— 实测这位用户答题序列的前后两半抽到的是几乎不相交的行情:

```
前半  2026-08 .. 2026-10
后半  2026-05 .. 2026-07 为主
```

机械全进 2:1 在前半是 +0.010 R/题、后半 +0.045 R/题。也就是说累计 R 曲线
那段上坡,**可能只是换了好做的月份**,而页面上原本没有任何东西会暴露这件事。

新面板按**题目的月份**(不是答题顺序)分组:每月一行,给出你每题 R、机械
每题 R、以及两者之差(超额);配一条当期走势线,底纹按超额正负着色。

走势线用的是**每天题目入场价的中位数**。所有题都在 11:31–14:30 决策,所以
那是一个**午盘价**,不是收盘价,界面上也这么写。线从整套题库取,不只取已答的
—— 否则跳过的日子会留下空洞。

### smoke.mjs

断言盯的是**坐标轴**:必须按题目月份分组、日历升序、且覆盖已答题涉及的每一个
月份。一个悄悄退回按答题顺序的面板看起来完全正常,却回答了另一个问题。

写第一版时这条断言红了,报「展示 2026-09,已答跨越 2026-08,2026-09」—— 是测试
自己的时序问题:它读的是更早一次 `report()` 留下的面板,而那之后又答了题。改成
先重新渲染再读。已验证把分组键改错会红。

## v0.53.0 — 先确认 OpenD 在，再去拉期权链 (2026-10-24)

### Fixed: OpenD 没运行时 viewer 打不开

`OpenQuoteContext` 在端口被拒时**不抛异常** —— 它在调用线程上无限重试。
而 `__init__` 末尾必须调一次 `_on_option_indicator_toggle()`(初始就勾上的
复选框不会发 `stateChanged`,不调的话期权墙永远不画),那一调就同步建 context。
结果:Options 开着而 OpenD 没起来时,**窗口根本不出现**。

实测 TCP 连接约 1ms 就被拒,而构造函数 20 秒后仍卡在 `network_manager.poll`。

现在先做一次 0.5 秒的端口探测,没人监听就直接跳过这一轮。期权定时器照常走,
`_trigger_option_fetch` 每个周期都会再调回来,所以 **OpenD 一起来就自己接上**
—— 不用点重连,也不用重开 viewer。

前后对比(把端口指向无人监听处):

```
HEAD      卡死（45 秒超时）
加探测后  2.96 秒建好，option_ctx=None，日志一行
```

日志只在状态变化时打 —— 每轮一行的话一分钟四条,等于没人看了。

探测只排除「没人监听」这一种情况,它便宜又常见;端口通着但 OpenD 自己卡住
仍然挡不住,那是另一回事。

### tests/analysis/test_opend_probe.py（新增）

8 条。核心那条测的不是「连接失败了」而是「**SDK 根本没被构造**」—— 因为
构造它本身就是卡死的原因,一个检查返回值的测试会连着卡 45 秒再红。

还有一条对齐探测和连接的地址:探一个端口、连另一个端口,上面每条都能过,
而线上照样卡死。

## v0.52.0 — 当天逐笔改为增量读取 (2026-10-23)

### Changed: 刷新不再整天重读 ticks.db

过去的日子已经按天缓存,但**今天**不能缓存 —— 它还在写,所以每一轮刷新都
把整天重读一遍。实测单日 2.5–8.7s,而同样每轮都跑的 SMC 全套只要 250ms,
这一个读取是其余所有东西的十到三十倍。这就是 refresh 下不到 1 秒的原因。

改完之后(同一台机器、同一个库):

```
2026-10-23        首次 2845ms   增量   2ms   提速 1424x   总量/桶集合与全量一致
2026-10-23 offex  首次 3457ms   增量   3ms   提速 1009x   一致
2026-10-22        首次 5962ms   增量   4ms   提速 1639x   一致
2026-10-22 offex  首次 7144ms   增量   4ms   提速 1681x   一致
```

### 为什么不是「读 ts 比上次大的行」

多笔成交共用同一个时间戳。`ts >` 会丢掉那一秒剩下的笔,`ts >=` 会把它们
数两遍。所以改成**从最后一笔所在的那个桶的起点重读,并整桶替换** —— 重读
的只有当前这一个未完成的分钟,总量由构造保证精确,没有任何边界算术可错。

交出去的 dict 不会被就地改写:每次合并都新建顶层 dict,因为上一帧画图的
东西可能还拿着它。

### S/M/L 阈值:唯一的近似

分档阈值是全天成交量的 p33/p67。要对增量来的行分档就得有阈值,而重算阈值
又要把之前所有行重新分一遍 —— 那正是要避免的事。所以阈值在全量加载时冻结,
当天的桶数涨到两倍时再做一次全量重载(一个交易日约十次,而不是每 15 秒一次
的 240 次)。

代价只落在 Tick Profile 的 S/M/L 三个勾选框上,而且形式是「某些单子落到
相邻档位」。总量不受影响,所以热力图、CVD、DCVD、Δ 柱、OffEx 全部精确。
三个框都勾上时 `buy_s+buy_m+buy_l ≡ buy`,连这点差异也看不见。

**SMC 完全不受影响** —— BOS/CHoCH、FVG、OB 都只吃 K 线,不碰逐笔。

### tests/analysis/test_tick_incremental.py（新增）

11 条,其中三条专盯上面那个边界:共用同一秒的成交不能翻倍、当前桶里新来的
一笔必须被看见、交出去的 dict 不能被改写。另有总量必须与全量加载逐项相等、
换标的/换日期/换 offex 要重新开始、桶数翻倍要重新取阈值。

## v0.50.1 — 黄灯的说明在一种情况下是假的 (2026-10-23)

### Fixed: 「身后两根都不是负的」有时身后就是负的

上一版把黄灯的理由统一写成这一句,但放宽规则之后多出一种情况:翻转在再前
一根,而紧接着那一根**已经越过 0.4** —— 绿灯在那一根亮过了,当前这根只是
延续。此时身后确实有负数,这句话会把你支去找一根图上明明就有的柱子。

测试报错时把它自己拆穿了:

```
身后两根 +0.89、−0.42 都不是负的，不算翻转。
```

现在分成三种理由:没到阈值 / 前面不够两根 / 翻转在再前一根但绿灯已经在中间
那根亮过(说明这根是延续)/ 身后两根确实都不是负的。

这种情况之所以存在,是因为**信号只亮一次**:一次翻转后连着两根都过阈值,
那是一个绿灯而不是两个,第二根必须说清自己是哪一种。

### Fixed: 开头说明里的 45% / 25% 也过期了

实际是 c1 39.8% / 27.0%、c0 41.6% / 23.4%。和写死的灯内计数同一个毛病,
同一个修法:从当前这套题的 rates 文件里读,文件到之前先不写数字。

## v0.50.0 — 绿灯的「翻转」允许晚一根 (2026-10-23)

### Changed: 翻转后晚一根才到 0.4，也算绿灯

原来要求 dr1 ≥ 0.4 **且前一根为负** —— 0.4 必须落在翻转那一根上。实测
这个限制没有依据:

| | n | 2:1 命中 | 平均 R |
|---|---|---|---|
| 翻转后立刻 ≥0.4 | 80 | 40.0% | +0.200 |
| 翻转后晚一根才 ≥0.4 | 25 | 40.0% | +0.200 |
| ≥0.4 但身后没有翻转 | 53 | 34.0% | +0.019 |
| 全部题目 | 893 | 33.6% | +0.008 |

差值 0.000,置换检验 p = 1.000。起作用的像是**翻转本身**,不是它发生在
哪一根:身后没有翻转的那组就掉回题库的基准率。

放宽后 c1 的绿灯样本 80 → 105。实盘上「翻转后第一根还没放量、第二根才
起来」很常见,原规则把这类全丢了。

**两点保留**:B 组只有 25 题,平均 R 的区间是 [−0.400, +0.800],正确的说法
是「测不出差别」而非「相同」;而且这是在题目自己的数据上挑规则,没有样本外
那一臂。所以放宽入选条件可以,但不该据此调高绿灯的预期。

### 绿灯和黄灯在 c1 上已经分不出来

顺带算出来的,写在这里免得以后又被当成新发现:

```
c1: green n=105 40.0% +0.200R   amber n=300 39.7% +0.190R   red n=430 27.0% −0.191R
c0: green n=118 46.6% +0.398R   amber n=235 39.2% +0.175R   red n=487 23.4% −0.298R
```

c1 上绿灯相对黄灯没有优势(40.0% vs 39.7%)。这套灯真正带信息的是**红灯
那一侧** —— 430 题、27.0%、平均 −0.191 R。c0 上绿灯仍然领先。

### Fixed: 灯里的数字不再写死

`44 题`、`186 题`、`386` 是手写进页面的,题库已经 893,每一个都错了。
现在 `drill_rates.py` 算出 `light` 段,页面从当前这套题的 rates 文件里读。
平均 R 仍由 `3p − 1` 得出而不单独存:凡是进了题库的题都触及过某一边障碍,
2:1 的交易只会付 +2 或 −1。

### tests/strategy/test_drill_rates.py（新增）

`light_of` 必须和页面的 `ruleLight` 一致,否则页面会拿一条规则的战绩去配
另一条规则的灯。九条用例盯的是两份实现最可能分叉的地方:中间那根必须**没到**
阈值(到了的话绿灯是它、不是这一根)、只放宽一根而不是「最近有过负的」、
以及 mark=0/1 时不能越过序列头部。

smoke 里加了对应的一条,并验证改回窄规则会红。

## v0.49.1 — 标出成交在哪一根 (2026-10-23)

### Added: 绿箭头指目标、红箭头指止损

判词一直写着「第 4 根触及目标」,但要在图上找到那一根得从决策线开始数蜡烛,
而目标线横贯整张图,眼睛没有着力点。现在直接在那根上画箭头:绿色指目标、
红色指止损。同一根里两边都碰到的,按判词一致算止损,画红的。

**只在那根被揭示之后才画。** 后面的 K 线是一根一根放出来的,箭头如果提前
画在还没揭示的区域里,它不会看起来像坏了 —— 它只是悄悄把答案说了。

箭头的位置是用答案自己的 ATR 倍数**对着当前画出来的蜡烛重算**的,不是读
记录里存的结果。记录里的 `stop` / `target` / `r` / `how` 是答题那一刻冻结
的,题库重新生成后同一个 id 下的 bar 可能变 —— 箭头是对某一根蜡烛的断言,
必须由屏幕上的蜡烛推出来。

`settle()` 现在返回 `hit`("tp" / "sl" / "both" / "none"),不用再去解析判词
的中文字符串来判断是哪一边结束的。

### smoke.mjs

断言找一道窗口内确实触及的题(超时的题没有可指的那一根,会空过),比较
「结算前一根」和「结算那根」的箭头填充数。已验证两种破法都会红:整个不画,
以及去掉揭示闸门让它每根都画。

### 一则查错记录

起因是报「上影线突破 TP 却不算 TP」。查下来结算判据本身没问题 ——
`q.h[j] >= target`,用最高价,上影线是算的;当时读到的那条竖线是 30 根结算
边界。但顺带查出页面上那题的数据是旧的:屏幕显示入场 179.32,而原始 K 线
2026-07-14 13:19 的收盘是 179.4401。题库在答题之后变过,这正是上面不读冻结
记录的原因。

## v0.49.0 — 习题新增第三类：夹角 (2026-10-23)

### Added: 夹角（DK 快线压向慢线）

现有两类的触发都是「又破了个低」—— 练的全是接一个已经跌下来的东西。夹角
是另一种几何:快线转头向下、与慢线收拢,而价格多半**还没破低**,所以现有
判据整个扫不到它。

判据:快线 3 根内向下,间距 5 根内收窄,且间距收到 **0.25 ATR** 以内、或刚
从上方交叉。边沿触发 —— 这个状态一成立就会持续几十根,只有它第一次成立那
根算一道题,否则同一段行情会铺出一串几乎一样的图。

110 个交易日出 104 道,每天 0.9 道。两套题分别到 885 / 888。

**它不是更好的入场,只是一个你做不好的形状。** c1 的夹角 2:1 命中 32.7%、
1:1 命中 51.0%,对比全集的 33.5% / 47.2%,n=104 的标准误约 4.3pp —— 都在噪声
里。加它是为了练,不是为了多一个信号。

### 夹角走自己的间隔游标

回落题的 `GAP` 游标如果和夹角共用,一道夹角就会把 15 根之内的那道回落题挤掉
—— 那是已存在、答案挂在其 id 上的题,会在重新生成时无声消失。所以分开。
`test_adding_it_does_not_displace_a_single_dip` 钉这个:同一天分别跑「只回落」
和「回落+夹角」,要求回落那条流逐条相同。已验证把游标改回共用它会红。

### PINCH_DIP_GAP = 5,不是 GAP

第一版要求夹角距上一道回落题也有 15 根,结果 110 天只出 **26** 道。原因是
夹角紧跟回落 —— 中位间隔只有 6 根,80% 落在某道回落题的 15 根之内。放宽到
5 根得到 104 道,同时仍排掉贴着回落题 1–4 根、在 120 根历史里看起来几乎是同
一张图的那些。

按「避免重复题」定这个数,不按胜率。8 根那档量出 39.5% 看着诱人,但 n=86,
而且用胜率选参数就是在题目自己的数据上拟合。

### 一处先前说法的更正

之前报过夹角与现有题「重合 7%」—— 那是**同一根 bar** 的重合率。按 ±15 根算
是 80%。两个数不矛盾,但 7% 会让人高估它的时间独立性。

### 两个消失的 id

`--replace` 全量重跑后 c1 少了 `2026-09-01_1356_浅回调` 和
`2026-09-10_1332_深回落`。一度以为是夹角顶掉的,关掉夹角单跑证伪:没有夹角
时那道深回落照样落在 13:35。这两行是更早版本生成、靠 append 合并一路带过来
的陈旧行,当前判据根本不产生它们,这次才被清掉。c0 的 784 个 id 全部保留。

### 为什么页面要自己做重排检验

上面那些总计是**对一堆题求和，换个顺序不会变**；而曲线只有顺序 ——
回撤、什么时候翻正、近 20 笔那条线，全是一次抽签的结果。最大回撤尤其
容易被读成关于人的事实，其实是关于洗牌的事实。

所以页面自己把同样这些笔重排 2000 次，报告实际序列落在哪个百分位，
并做趋势的置换检验和总 R 的 bootstrap。这样随着题目增加，结论跟着更新，
而不是钉一个当时测过的数。

当前这 92 笔的实测：

```
胜率 45.7%（42/92）      95% 区间 [35.9%, 55.8%]
盈亏平衡需要 44.7%        均盈 +1.19R / 均亏 −0.96R
累计 +1.96 R             bootstrap 95% [−19.1, +23.9]
最大回撤 −7.85 R          重排 20000 次后落在第 85 百分位（比典型更浅）
趋势相关 −0.006          置换检验 p = 0.95
前后两半每笔差 +0.012 R   置换检验 p = 0.96
```

出题的随机打散对统计是好事：它让题目难度与答题位置脱钩，真出现趋势时
那是答题者的变化，不是题目先易后难。代价是横轴是顺序，不是日历。

`smoke.mjs` 补了四条断言。`drawCurves` 包在 try/catch 里（一张图挂掉不该
带走成绩单），这意味着静默失败是可能的 —— 断言是那个 catch 能留着的前提。

## v0.46.0 — 场外分类改成增量：17.3 分钟 → 1.2 秒 (2026-10-20)

### Fixed: 夜盘 OffEx 一直显示 N/A

起因是用户报「场外 OFFEX 显示 N/A」。三个库对了一下时间：

```
ticks.db       最后一笔  23:40:50
order_book.db  最后快照  23:40:50     ← 原料是齐的
tick_mid.db    最后一笔  20:30:04     ← 只有这个停了
```

`tick_classify` 的 cron 是 `30 20 * * 1-5`，一天跑一次。20:30 正好卡在
盘后收盘（20:00 ET）刚过，而夜盘 20:00–04:00 还在收数据——**结构上就
覆盖不到紧随其后的八小时**。viewer 把曲线停在最后一根有分类的 bar、
后面填 NaN（这是 v0.44.0 故意做的，不让未分类的 bar 当 0 累加、看着像
「场外流量稳定在 −22K」），于是整夜悬停都读 `off n/a`。

### 为什么一天要 17 分钟

量出来的，不是估的：

```
今日盘口快照  384,119 条（约 5 次/秒）
单条 JSON     约 1,481 字节
一次运行要 json.loads 0.57 GB —— 而且每次都从 00:00 重来
```

`_midpoints()` 把一整天的 `ob_snapshots` 全读出来逐条解析，只为取最优
买卖价两个数。docstring 里写的「约 22 秒」早就不成立了。

顺带暴露：每晚 `--days 3` ≈ 52 分钟，而 scheduler 的
`communicate(timeout=1800)` 是 30 分钟——**每晚都超时**，记一条 failed
但子进程没被 kill、继续写库，日志与实情相反。那 3 天里有 2 天早就签完，
`put` 是 REPLACE，算出来一模一样，白跑 35 分钟。

### Added: 断点续跑

`classify_ticks.py` 默认从**这一天已经签到的最后一笔**往后算，只解析
上次运行之后新增的那段盘口。当天一条都没签过时仍然整天跑，所以频繁的
cron 不需要额外的 seed 作业。

窗口往回多读 `RESUME_OVERLAP = 5 分钟`。逐笔不是按到达顺序严格有序的，
一笔 tick 可能在运行扫过它的时间点之后才落进 ticks.db；没有这段重叠，
下一次从它后面开始，它就永远签不上。五分钟的盘口约 1,500 条，相对一天
的 384,000 条等于不要钱。

新增 `--full`（整天重算，即原行为）和 `--since`（显式指定窗口起点）。
`TickMidStore.last_ts()` 用 `ORDER BY ts DESC LIMIT 1` 而不是 `MAX(ts)`：
主键以 (code, ts) 开头，只走一个索引项，空区间返回无行而不是一行 NULL。

### Changed: cron `30 20 * * 1-5` → `*/20 * * * *`，days 3 → 2

续跑之后，没有新数据的一次运行只要几秒，cron 就不必稀疏了。去掉
weekday 限制是因为周五夜盘跨到周六，那些 tick 落在周六这个日历日上，
`1-5` 永远不会去看。days 降到 2 覆盖跨午夜，三天那是用来兜住漏跑的，
20 分钟的节奏兜得更好。

### 实测

```

--days 2 续跑           1.2 秒
```

补跑后 `tick_mid` 最后一笔 00:15:32，`ticks.db` 00:15:41 —— **落后 8 秒**。

## v0.45.0 — 规则定型为三变量；红绿灯；一批否定结论 (2026-10-19)

做多   dr1 ≥ +0.4  且  前一根 dr1 < 0

| 模块 | 问的问题 | 答案 |
|---|---|---|

### 为什么不做 GRU

约束在样本不在架构：45 个样本外交易日对上千参数。梯度提升树拿到全部 25 个
特征、能找任意交互作用，与三变量规则打平——那说明这些变量里没有线性之外的
结构，换架构不会变出来。另有两条旁证：LSTM 吃订单流序列 AUC 0.528（单变量
0.639），以及上面的马尔可夫阶数检验。

### 过程中纠正的三处自身错误

- **`absorption.py` 的前视泄漏**：`x = OFI / S` 的 S 漏了 `.shift(1)`，

- **把规则说成两变量**：模型的特征里也没有翻转，所以「树拿到全部特征都
  打不过」是对一个模型没见过的规则说的。
- **笔数未对齐就比较**：拿 GBM 和两条不同笔数的规则比，说法在中间换了。
  对齐并配对之后，六个比较全部「分辨不出」。

## v0.44.0 — 吸收研究；DCVD 补上「量」这一维；订单墙标注与习题热力图 (2026-10-19)

### Added: `backtest/absorption.py` — 吸收信号，事先登记，结论是否定的

把「量大价不动」写成可检验的形式。不是比值 `dp/成交量`（量趋零时爆炸，
且把安静的 bar 算成吸收），而是对**局部价格冲击的残差**：

```
y = dp/ATR            x = OFI / 前 60 根总量中位数
λ = y 对 x 的回归斜率（前 60 根，过原点）
A = (y − λx) / sd     正为看涨吸收
G = 前 60 根 |x| 的 80 分位     触发 |x| ≥ G
```

四个滚动量（S、λ、σ、G）窗口上界都是 t−1，bar t 不参与评判自己的那条线。

**吸收不只是无效，是反的。** 60 个前推样本外交易日：

|---|---|---|
| 基准（多/空） | 19196 | −0.101 / −0.072 |

| **吸收做空** | 227 | **−0.566** |
| **大卖量顺势做空** | 2399 | **+0.352** |
| **大买量顺势做多** | 2178 | **+0.285** |

同一道流量门槛，顺势 +0.35、逆势 −0.36，三个阈值两个方向全部同号。

**符号不翻转**。A 与 dr1 相关系数 −0.012，所以这个否定不是「A 只是 dr1
换个写法」——它是独立维度，携带的是负信息。

## v0.43.0 — 全量回测：delta_r × ATR 矩阵与前推验证 (2026-10-17)

### Added: `backtest/delta_atr_matrix.py`

| 维度 | 取值 |
|---|---|
| 周期 | Wilder n = 5 / 7 / 10 / 14 / 21 / 30 |
| 平滑度 | 原始 / SMA5 / SMA10 / EMA10 / EMA20 |

### Added: `backtest/walk_forward.py`

**挑选这个动作本身**（每折重新排序取第一名——这才是实际会做的事，也是
网格通常死掉的地方）。

### 结果

| 规则 | 笔数 | 净 R (1:1.5) | 95% 区间 |
|---|---|---|---|
| 基准：每一分钟 | 22500 | −0.101 | [−0.141, −0.064] |
| dr1 ≥ 0 | 11053 | +0.100 | [+0.059, +0.143] |
| **dr1 ≥ 0.4** | 3897 | **+0.207** | [+0.147, +0.266] |
| **dr1 ≤ −0.4（做空）** | 4256 | **+0.247** | [+0.196, +0.300] |

两侧相对各自基准的增量是 **+0.308 / +0.309**，三个 RR 上一致——
delta_r 对两个方向的预测力相同。空头净 R 更高是因为三倍杠杆 ETF 的波动
衰减给空头一个结构性顺风，不是信号更好。

**ATR 的四个维度全部单调改善**（周期越长、平滑越重、越不判方向越好），
但作为边际贡献清不过噪声：固定 `dr1≥0.4` 后，事先选定的
`ATR14 原始 斜率10` 增量是 +0.081 [+0.003, +0.161]，勉强擦线。
三条单调性合起来说明 ATR 在这里不是择时信号，只是个慢速的波动率状态开关。

**基准胜率贴着打平线**（49.4% / 44.3% / 40.0% / 36.7% / 33.7%

- 自助法**一律重采样交易日而非分钟**。
- 「某一项值不值」是差值，用**同一次重采样配对**计算；两个各自的区间是否

## v0.41.1 — 盈亏平衡胜率算错了，和总 R 自相矛盾 (2026-10-17)

### Fixed: 用计划目标算盈亏平衡，而不是实际拿到的

```
入场后胜率              22 / 53 = 42%
这个盈亏比的盈亏平衡胜率   39%  ✓ 够了
你的总 R                −3.74            ← 同一张表上
```

39% 是拿**平均目标 1.57 R** 算的，等于假设每笔盈利都吃满目标。实际吃不满：
既没碰止盈也没碰止损的单子在第 30 根按收盘结算，只拿到一个零头，它们算进
胜率却几乎不贡献 R。所以这张卡会在亏 3.74 R 的同时宣布"够了"。

现在用**实际的平均盈利和平均亏损**算，并把两个数直接列出来：

```
实际 平均盈利 / 平均亏损    +1.18 R / −1.00 R （计划目标 1.57 R）
按实际盈亏算的盈亏平衡胜率   46%  ✗ 还不够
```

计划和实际差 10% 以上时，「读法」里会写明机制：止损 1.99 ATR 配 1.57 R 等于
把止盈放到 **3.12 ATR** 之外，而 30 根内走到 +2 ATR 的概率只有约三成。

## v0.36.0 — 习题逐根播放，止损与止盈解耦 (2026-10-15)

### Changed: 后续 K 线一根一根放，不再一次揭晓

提交之后图表停在决策那一根，按 **▶ 下一根**（方向键 →）走一根，**⏩ 自动**
（空格）自动播到结算那一根为止，**⏭ 全部** 直接看完。计数器写明「第 n / N 根
（第 k 根结算）」。

一次性揭晓只能告诉你对了还是错了；盘感要练的是看着它一根一根走出来。横轴
仍按整个窗口铺开，所以播放时蜡烛只在右侧填充，不会左右跳动。

### Fixed: 拉止损会把止盈一起拖走

目标原先以 **R** 为单位，而 R 是止损距离的倍数，所以动止损就等于动目标 ——
想「放宽止损但目标不变」做不到。

现在两条都按 **ATR** 独立设定：

    stop   = entry − stopAtr × ATR
    target = entry + tgtAtr  × ATR
    R      = tgtAtr / stopAtr        ← 由两者相除得出，不再是拨出来的

盈亏比变成显示值而不是输入值。结算逻辑不变：触及目标记 `+R`，触及止损记
`−1`，同一根里两边都碰到按最坏算，30 根内都没碰到按收盘价折算。成绩页的
1:1 / 2:1 基准线不受影响（1 ATR 止损 + 2 ATR 目标仍然就是 2R）。

### Changed: `strategy/drill/smoke.mjs` 加了这两件事的断言

冒烟测试现在直接验证「只动止损时目标纹丝不动、R 等于 tgtAtr/stopAtr」，以及
「播放从 0 开始、两端都收得住」。这两条都是肉眼看不出坏掉的那种。

## v0.33.0 - shelves that survive a change of bin count, and a cache that admits what it is missing (2026-10-14)

### Rewritten: `strategy/session_vp/profile.py` -- `find_nodes`

The old version read peaks off a histogram binned into the session's range, so
the bin count decided the answer: SOXL 2026-10-12 reported one shelf at 30 bins
and two at 100, and the main shelf's share of volume slid from 36% to 18% across
that range. Nothing about the session changed; an arbitrary parameter did.

Three faults, found by drawing the profile rather than by reasoning about it:

* **Bin width tracked the day's range.** A quiet session and a wild one were cut
  into bins several times apart, so no peak rule could behave the same way on
  both. Binning is now anchored to price (`bins_for_price`) and the smoothing is
  a Gaussian whose width is stated as a share of price. The bin count drops out:
  100 through 800 bins agree to within three cents, which is a test.

* **`min_peak_frac` measured peaks against the tallest one.** A shelf had to
  reach 35% of the session's busiest price to count, so a small, cleanly
  separated shelf never did. This is the same mistake as normalising the
  liquidity heatmap against its global maximum, which blacked out thin levels.
  Prominence replaces it -- how far the profile falls before it climbs again,
  which is local and is the question actually being asked.

* **Edges ran to half height without stopping at the valley.** A tall peak's
  skirt ran through the dip and up into its neighbour; the spans then overlapped
  and merged, so *lowering* the prominence threshold returned one shelf spanning
  $4 instead of several. Edges now stop at half height or the valley, whichever
  comes first, and shelves cannot overlap by construction.

`find_nodes` returns `Node(lo, hi, peak, share)` -- `peak` being the shelf's own
POC, which the old 3-tuple had no room for. Prominence 0.25 was set by eye
against two sessions, 2026-10-12 (one shelf with a shoulder above it) and
2026-10-07 (three), and both are reproduced.

The 60.2%-against-27.3% result for "did the entry land inside a node" in
`doc/session_performance.md` was computed with the old definition and needs
rerunning; the note there says so.

### Fixed: `feeds/fetcher.py`, `feeds/kline_store.py` -- cache coverage

`_cache_covers` compared the requested range against the first and last bar in
the cache. A cache with holes in the middle passed, `load()` returned short, and
nothing ever repaired it: once the endpoints are wide, every later request
matches. The seven-day boundary tolerance, meant for weekends, is longer than a
trading week, which is how a cache ending 2026-10-07 came to "cover" a request
running through 2026-10-12.

Six weekdays had gone missing this way between May and October 2026 --
2026-09-11, 09-29, 09-30, 10-01, 10-08 and 10-09 -- out of 106. They are
refetched and the window is now complete.

Coverage is recorded per day in a new `kline_coverage` table when a fetch
completes, which also settles holidays without a calendar: a day inside a span
that was fetched and holds no bars is a day the market was shut. An existing
cache seeds itself from the days that hold bars, so its holes stay visible and
repair themselves on the next request, and `force_refresh=True` clears coverage
for the range so a fetch that came back empty for the wrong reason can be
retried.

Sundays are checked as well as weekdays -- the week opens at 20:00 on Sunday and
those bars carry its date. Days from today onward are never required, and today
counts as present once it holds a bar, so repeated intraday calls stay off the
API without a partial session being frozen into the table.

### Fixed: `feeds/kline_store.py` -- a day fetched mid-session was frozen

`missing_days()` carefully refuses to call a running session complete.
`mark_covered()` walked straight past that and recorded every day in the fetched
range, today included. A fetch at 12:02 on 2026-10-13 stored 152 of the
session's 390 bars and marked the day covered, so every later call trusted the
cache and the afternoon never arrived. The day was invisible to anything that
required a full session -- which is how it was found: an RSI study reported no
oversold minutes at all on a day that had plenty.

`seed_coverage()` had the same hole and now takes the same guard. One day was
affected across 435 covered weekdays; its coverage was cleared and refetched.

A remaining limit is recorded in the tests rather than hidden: seeding knows
only whether a day holds bars, so it cannot tell a partial day from a whole
one. That is tolerable because seeding is a one-time migration that no-ops once
anything is covered -- which is why this truncation came from `mark_covered`.

## v0.30.0 — off-exchange flow as its own line (2026-10-07)

### Feat: `OffEx` draws off-exchange flow beside CVD (`analysis/trade_viewer_qt.py`, `feeds/tick_mid_store.py`, `scripts/classify_ticks.py`)

The feed leaves 57.5% of SOXL's volume NEUTRAL, and that volume is

leads the next minute's return at **-0.177**. Uninformed flow, which is what
makes a divergence with the exchange side worth looking at.

### Correction: the earlier case for merging was circular

An earlier measurement put the combined correlation at +0.320 against +0.276
for the feed's tags. That used midpoints of unlimited staleness. Against a
stale midpoint, "price above the mid" largely restates "price has risen since",
so correlating it with the return is close to tautological. Tightening the
limit shows it plainly:

| book staleness | neutral alone | combined |
|---|---|---|
| 0.2s | +0.056 | +0.225 |
| 1s | +0.149 | +0.255 |
| 5s | +0.196 | +0.284 |
| unlimited | +0.253 | +0.320 |

A better midpoint should classify better, not worse. It reads the other way
because the number was measuring the price move.

## v0.29.0 — DCVD, the CVD slope normalised to [-1, +1] (2026-10-06)

### Feat: a bounded order-flow oscillator (`analysis/trade_viewer_qt.py`)

CVD's slope says how hard flow is pushing, but its units are shares, so the
same reading means different things on a quiet day and a busy one. DCVD divides
that slope by the largest slope the same bars could have produced -- every
classified trade on one side:

    DCVD = sum(buy - sell) / sum(buy + sell)   over the last DCVD_LOOKBACK bars

Bounded by construction rather than by a fitted scale, so 0.4 reads the same in
any regime. A new subplot (indicator `DCVD`), green above zero, red below,
y-axis pinned to the bounds and mouse-zoom disabled on it -- auto-ranging would
undo the normalisation it exists for.

**Two choices the data settled, both measured on SOXL 1m over three days:**

*NEUTRAL is excluded from both halves,* matching the CVD delta. It is 57.5% of
the tape; in the denominator it damps the median bar to 0.08 and the range past
±0.5 goes unused. Excluded, the median is 0.19. The trade-off is that DCVD
describes flow that could be classified, not all of it.

*Lookback defaults to 10 bars.* At 1 bar, 14.7% of bars pin past |0.9| -- a
single minute's classified flow is often entirely one-sided, so the indicator
lives on its rails. At 10 bars that is 0.4%:

| lookback | median | p99 | past 0.9 |
|---|---|---|---|
| 1 | 0.477 | 1.000 | 14.7% |
| 5 | 0.241 | 0.892 | 0.9% |
| 10 | 0.190 | 0.768 | 0.4% |
| 30 | 0.143 | 0.744 | 0.0% |

Live over 4,161 bars it ranges -0.944 to +0.920 with 0.41% past |0.9|.

Bars with no tick coverage add to neither sum, so the line holds through a gap
instead of reading as balanced flow.

**Not a signal on its own:** correlation with the next bar's return is +0.011,
i.e. none. It measures what flow has done, not what price will do.

The counts are now derived from an hours target (`_keep_for_hours`) rather
than written down, so a future rate change is a one-line edit with a visible
consequence instead of a silent one. SOXL keeps **24 hours** (535,680
snapshots, ~1.1 GB); other codes keep one regular session, 6.5 hours
(145,080, ~0.3 GB each). Sizing uses the regular-session rate, the densest
one, which makes the hours target a floor across every session.

## v0.20.0 — one row per order-book snapshot (2026-09-21)

### Feat: the collector stores every push instead of one every 2s (`feeds/order_book_store.py`, `analysis/order_book_collector.py`)

The old schema stored one row per price level and the collector rate-limited
writes to one snapshot per code per 2s, because 140 levels x every push was
judged too much to write. A push-rate probe run against the live feed settled
what that was costing: ORDER_BOOK arrives on a fixed ~300ms cadence (p90 =
0.302s in all three samples) with activity-dependent bursting, and **zero
duplicate books** -- 1.0 push/tick overnight, 2.25 at the open. Nothing was
being deduplicated away; the throttle was discarding distinct books.

`ob_snapshots` now holds one row per snapshot, with the two sides as JSON, and
the throttle is gone. **12x more snapshots stored** -- 0.5/s before, 6.2/s
measured after, median inter-snapshot gap 0.291s.

Identity is `rowid`, deliberately not `(code, ts)`. An intermediate version
used that as a primary key with `INSERT OR REPLACE` and lost books: the feed
bursts several distinct books 12-19ms apart while `datetime.now()` on Windows
only advances in ~15.6ms steps, so 30 pushes stored 9. Reads order by
`ts DESC, rowid DESC` and `prune` counts rows, not timestamps.

### Fix: a locked book is not a crossed book (`feeds/order_book_merge.py`)

The cross guard tested `best_bid >= best_ask`, throwing away every snapshot
where the two sides quoted the same price. That is a routine state -- two
venues on the same price before the trade prints -- and it clusters around the
open, which is when the heatmap can least afford a hole. Only `bid > ask` is
physically impossible.

It surfaced now because removing the write throttle let all ~6 pushes/s reach
the merger, filling the console with
`crossed book bid=141.44 >= ask=141.44 (both/neither side fresh), skipping`.
Warnings for genuine crosses are now throttled to one per code per 5s with a
suppressed count on the next one through; throttling the log never affects
whether the snapshot is skipped.

### Fix: definitions lost to an index-based refactor (`analysis/liq_hm_window.py`)

The refactor that routed every read through `OrderBookStore` replaced a block
between two text anchors by index, and the end anchor sat further down the file
than intended. It also took `_TICK_DB_PATH`, `_query_ticks` and four
`QThread`/`QObject` classes -- among them `_PushBridge`, which `__init__`
instantiates. Opening the heatmap raised `NameError` while the whole suite
still passed, because nothing in it ever built the window.

`tests/analysis/test_gui_window_smoke.py` now constructs `LiqHmWindow` and
`DomWindow` offscreen. Confirmed to fail if `_PushBridge` goes missing again.

### Fix: two scripts were reading a frozen table (`scripts/check_db.py`, `scripts/analyze_absorb_price_change.py`)

Both still queried `order_book_snapshots` directly after it stopped being
written, so they reported a 325-snapshot pruning remnant as if it were live
data. Adds `earliest_ts()` and `codes()` to the store, which is what they were
hand-rolling as `MIN(ts)` and `SELECT DISTINCT code`.

### Migration

`order_book_snapshots` is no longer read or written. `OrderBookStore.
drop_legacy_table()` removes it; a `VACUUM` afterwards reclaims the freed
pages (96% of a 308MB file in practice). Neither runs automatically.

## v0.19.0 — incremental live kline fetch, Refresh down to 1s (2026-09-21)

### Feat: live cycles top up a cached frame instead of re-pulling the window (`analysis/trade_viewer_qt.py`)

Every live refresh re-fetched the whole lookback window: four paginated
`request_history_kline` calls (1m looks back 5 days, ~7200 bars at 2000/page).
That dominated the cycle and is why `Refresh(s)` had a 5s floor -- at 1s it
would have been ~240 history calls a minute, well past the API's limits.

A live cycle now hands last cycle's frame back to the fetcher, which tops it
up with a single `get_cur_kline` and merges. **One API call per cycle instead
of four**, and no re-parse of bars that have not changed. **`Refresh(s)`'s
floor drops from 5s to 1s**, validated live at 1s.

Correctness rests on two things:

- `_merge_klines` **overwrites** on an equal `time_key` rather than appending
  only unseen ones. The newest bar is still forming, so the same key returns
  with a different close/high/low/volume; keeping the first copy would freeze
  the live bar. The old `get_cur_kline` supplement had exactly that blind spot
  -- it filtered to unseen keys -- which went unnoticed only because the full
  re-pull replaced the frame every cycle anyway.
- Gaps are **detected, not predicted**. `get_cur_kline` returns the most
  recent `_CUR_KLINE_BARS` (200) bars, so it can only bridge a shorter gap.
  Rather than reason about elapsed time, the fetcher compares its oldest
  returned bar against the cache's newest and falls back to a full fetch when
  bars are missing between them -- correct however long the app was asleep,
  paused or disconnected.

The cache is `_klines` itself, keyed by `(code, tf)`, so a symbol or timeframe
switch cannot top up a frame with the wrong bars. Historical mode never tops
up; its window is pinned to a date rather than rolling. The merged frame is
trimmed to the same rolling start the full fetch would have used, so it does
not grow all session. A full fetch still happens on connect, on a code or
timeframe switch, and on any detected gap.

### Known: the remaining cost at 1s

The API cost is solved, but the per-cycle local work is not: `load_local_ticks`
re-reads the whole day's ticks (~181ms measured) and `_render()` repaints
1500 bars with all overlays (~205ms). At Refresh=1s that is roughly 20% of
wall-clock spent redrawing. Usable -- confirmed at 1s -- but the next
bottleneck if it needs to go lower is the tick reload, which could be made
incremental the same way.

### Fix: top-right tick profile went stale on the newest candle (`analysis/trade_viewer_qt.py`)

The tick profile panel is hover-driven: it repaints when the cursor moves to a

## v0.18.0 — push-driven Liquidity Heatmap (2026-09-20)

### Feat: the heatmap consumes the ORDER_BOOK push feed directly (`analysis/liq_hm_window.py`)

The heatmap used to read the collector's database on a 1s timer, so its
latency was the collector's 2s write throttle plus that poll: up to ~3s from
a book change to a pixel. It now subscribes to ORDER_BOOK itself and repaints
on the push.

Measured during the 2026-09-20 overnight session with the new probe: moomoo
pushes on a **~300ms cadence** (2,001 pushes in 600s; p10 0.294 / median 0.300
/ p90 0.306 -- regular enough that it is clearly a fixed server-side interval,
not market activity), and the collector's throttle was discarding **85.7%** of
them. End-to-end latency goes from ~1.5-3s to ~300ms, which is the feed's own
floor.

- `_PushBridge` carries snapshots from the SDK's socket thread to the GUI
  thread via a queued signal; the handler only merges and emits.
- Merging is `feeds.order_book_merge.OrderBookMerger`, shared with the
  collector, so partial pushes, side staleness and crossed books are handled
  by the one implementation that has been through production.
- The rightmost column is repainted in place while the Col(s) timer still
  rolls a new one on schedule, so the x axis stays a uniform time grid with a
  live edge. Appending per push would make it non-uniform and unreadable.
- Every push now lands in `_raw_snaps`, where before only the throttled writes
  did -- iceberg and spoof detection look for volume refreshing at a price, so
  they see every refresh the feed reports instead of one sample per 2s.
- A watchdog re-subscribes after `_PUSH_STALE_SECS` (90s) of silence from a
  feed that had been delivering. An OpenD subscription can stop delivering
  with no error surfacing, and a frozen heatmap looks exactly like a quiet
  book. Silence *before* the first push does not count, so opening the window
  hours before the session starts does not churn.
- The DB is still read for the cold-start pre-fill, and the old polling path
  survives as a fallback when the subscription fails or has not delivered yet.

### Refactor: shared ORDER_BOOK merge module (`feeds/order_book_merge.py`)

`order_book_collector.py`'s partial-push handling, side-staleness window and
crossed-book attribution move into `OrderBookMerger`, shared by the collector
and the heatmap. Pure by design: a push goes in, a complete snapshot or None
comes out; throttling and persistence stay with the collector. Verified
behaviour-identical to the inline original over 7 hand-built cases and 40
randomised push sequences, comparing the full write series.

### Fix: overlay markers froze on the push path (`analysis/liq_hm_window.py`)

Found during live validation. The push path did not call
`_redraw_orderflow_markers()` / `_load_absorb_ticks()`, so aggressor bubbles
stayed on the column they were first drawn on while the grid scrolled out from
under them. They now refresh on the column roll -- a push moves no column, and
redrawing at 3.3/s would be wasted work. `Reset` repaints the overlays too; it
only rescaled the axes before, which is why it appeared to do nothing.

### Tooling: ORDER_BOOK push-rate probe (`analysis/ob_push_probe.py`)

Times every push and reports the gap distribution plus what the collector's
throttle would discard. Writes nothing, so it runs alongside the collector.
`order_book.db` cannot answer this on its own -- every gap measured there is
floored by the throttle, not by the feed.

### Test: throttle coverage the collector never had (`tests/analysis/test_order_book_collector.py`)

`test_handler_accumulates_session_count` had been failing for as long as the
throttle existed: it called `on_recv_rsp` twice back to back and asserted both
writes landed. It now isolates accumulation from the throttle, and two new
tests cover the throttle itself (a burst inside the window produces one write;
the throttle keys on code). Confirmed by mutation.

### Known, not addressed

`order_book_snapshots` stores one row per price level, so a snapshot is ~120
rows, and `prune(keep=1000)` is row-based -- each code retains only 8-9
snapshots (~18s of history). That is why the pre-fill is so short. Removing
the collector's throttle is not viable until this changes: at the measured
3.3 pushes/s the current schema would write 400 rows/s (~0.94 GB per regular
session per code), which is what the throttle was added to prevent. One row
per snapshot would make it 3.3 rows/s.

## v0.17.1 — fix blank tick panel after using VP mode (2026-09-13)

### Fix: turning `VP` off left the tick profile panel blank (`analysis/trade_viewer_qt.py`)

Once VP mode had been used, switching back to the order-flow view showed an

- Verified on real ticks.db data (SOXL 2026-09-10): the order-flow X range

## v0.16.0 — session-profile POC hysteresis + POC trail (2026-09-10)

### Feat: POC switch hysteresis and a POC1/POC2 trail in the session profile (`analysis/trade_viewer_qt.py`)

The session profile's POC is a from-scratch `argmax` on every rebuild with no
memory of the last one, so on a two-cluster profile it teleports between the
peaks as their totals cross. Observed on SOXL 2026-09-10: four flips across
$5 (123.8 <-> 118.7) inside twelve minutes, and 91 POC changes over the day.

- **Hysteresis** (`Hold:` spinbox, default 5%, 0 disables): a rival cluster
  must hold that much more volume than the one the POC currently sits in
  before the POC moves. On the day above this takes 91 switches down to 4,
  and removes the 12-minute flip-flop entirely, leaving one decisive move.
- The comparison is over a **cluster**, not a bin. A single bin's volume is
  far too noisy to gate on: the profile is re-binned from scratch over a
  lo/hi that grows with the session, so a peak bin routinely hands a big
  slice of its volume to a neighbour. Measured rival/held single-bin ratios
  of 1.6-2.3 inside what was visually one stable cluster, which a percentage
  margin cannot separate from a real move. `_cluster_mass()` sums a fixed
  price window (`_POC_CLUSTER_PCT`, 0.5%) around each candidate instead.
- A held POC is reported at its own stored price rather than re-snapped to
  the nearest bin centre each rebuild, which would make it jitter a few cents
  on its own as the bin boundaries shift.
- **POC trail** (`POCs:` spinbox, default 2, up to 6): POC1 is the current
  level, POC2 the one it moved off, and so on, newest first — the pair reads
  as a direction of travel. Older entries fade and are dotted; levels closer
  than half a bin count as the same level. The trail resets when the profile
  is redefined (symbol / date / mode / range / bins / session filter), since
  a POC over a different set of bars is not a previous position of this one.
- `_compute_poc_vah_val()` takes an optional `poc_idx` so the value area
  expands from the held bin, keeping POC and VAH/VAL agreeing on the peak.
  VAH/VAL are widened to contain the held POC when the area collapses onto
  its own bin — a sub-bin correction that restores VAL <= POC <= VAH.

- Execution is now inferred from **spread movement**: if the best bid (BID order)
  fell below the price level, or the best ask (ASK order) rose above it, between
  appearance and disappearance, the order was consumed — not a spoof.
- `min_vol=0` auto-computes the threshold as the **median volume** of the most
  recent OB snapshot, adapting to each ticker's liquidity automatically.
- Each reappearance of a large order after a prior spoof/disappearance is treated
  as an independent new event with its own ▲/▼ marker.

### New: Absorption detection (`analysis/orderflow_detect.py` + DOM window)

Detects price levels where large passive orders held against significant aggressive
flow within a single bar window.  Three conditions must all pass:

1. **Passive wall** ≥ `avg_tick_vol × Pass` (resting order large enough to matter)
2. **Aggressive volume** ≥ `avg_tick_vol × Act` (real pressure applied — split orders
   accumulate naturally, so fragmented aggression is captured equally)
3. **Hit ratio** = `agg_vol / pass_vol` ≥ `Hit%` (meaningful fraction was attempted)
4. Resting volume at window end > 0 (level still present = not broken through)

Window is bar-aligned: `[candle_start(now, tf), now]` in live mode;
`[time_key − tf, time_key]` in historical mode (moomoo time_key = bar end).

`avg_tick_vol` = session average volume per trade — adaptive to instrument
liquidity without manual calibration.

DOM toolbar controls: `[✓ Absorb]  Pass:[3.0]×  Act:[1.0]×  Hit:[30]%`

Display: gold outline = ASK absorption (sell wall held); blue outline = BID
absorption (buy wall held).  Hover tooltip shows aggressive vol, passive vol,
and hit ratio for flagged levels.

`tests/analysis/test_orderflow_detect.py`: 17 new tests for `detect_absorption`
covering edge cases, each threshold condition, split-order accumulation,
direction filtering, and simultaneous bid/ask detection (36 total, all pass).

## smc_v2.3 (2026-05-29)

### Market Structure — `determine_trend` veto rule

**Old behaviour** (smc_v2.2): A CHoCH set `consecutive = 0`, requiring at least
one same-direction BOS in the rolling window before the trend was confirmed.
This was too strict and suppressed valid entries when no confirming BOS had yet
appeared.

**New behaviour**: CHoCH immediately confirms the trend (`consecutive = 1`), but
any BOS in the *opposite* direction that appears **after** the last CHoCH vetoes
the trend → `determine_trend` returns `None`.  This correctly rejects the
`[CHoCH bear, BOS bull]` pattern (market reclaimed the structural level) while
allowing clean CHoCH-only setups.

### Market Structure — BOS scan boundary fix (`detect_bos_choch`)

The inner break-scan now starts at the current swing bar itself (`sw["idx"]`,
inclusive) and stops before the next swing of the same kind.  Previously the scan
started at `sw["idx"] + 1`, which caused the scan to skip the swing bar even when
its close already exceeded the prior-swing wick — resulting in a BOS line drawn to
a lower, later bar that visually crossed over the obvious structural high.

### Backtest — per-stock output subdirectories

Each stock's log, CSV, PNG and HTML report are now written to a dedicated
subdirectory `<run_dir>/<CODE_slug>/` (e.g. `results/…/US_NVDA/`) instead of all
files landing flat in the run root.

### Backtest — self-contained HTML reports

`report.py` now embeds the full Plotly JS bundle inline (`get_plotlyjs()`) instead
of a CDN `<script>` tag.  Reports open correctly in air-gapped / restricted
networks and do not require an internet connection.  File size increases by ~3 MB.

### Backtest — UTF-8 config loading on Windows

`_load_json_config` in `run.py` now opens JSON files with `encoding="utf-8"`,
fixing a `UnicodeDecodeError` on Windows (GBK default locale) when config files
contain non-ASCII characters.

### Backtest — infinite `profit_factor` guard

`_cap_inf_pf()` in `report.py` replaces `float("inf")` in the
`profit_factor` column with the largest finite value before passing the DataFrame
to stats functions, preventing `RuntimeWarning: invalid value encountered in double_scalars`.
